# Submission manifest

Create a fresh template with `submission.py init`. Keep the JSON machine-readable;
no comments. Use null for unavailable optional fields and explain unknown identities
in notes. Do not copy a station.yaml, environment dump, token, private checkpoint
path, or entire session directory into the submission.

## Station and package

- `schema_version`: 1.
- `created_utc`: generated by init; preserve actual date.
- `station.id`: stable public ASCII label, e.g. `lab-a-station-02`; unique among contributors.
- `station.embodiment`: actual robot/arm configuration, e.g. a public model name and
  single/dual-arm configuration. Include gripper/tool if it affects visible behavior.
- `station.os`: actual OS/display environment (e.g. Linux Wayland).
- `station.manimux_commit`: revision of the running checkout, or null if unknown.
- `station.manimux_dirty`: true/false/null; do not include unrelated diffs.
- `content_reviewed_for_sharing`: true only after clips and metadata were inspected.
- `notes`: limitations and deviations, including any recorder-induced slowdown.

## Each take

- `id`: distinct within the submission; use `take-001`, etc.
- `task_prompt`: the actual task, in English for the editor.
- `evidence_mode`: `real_robot_policy`, `teleoperation`, `replay`, or `synthetic`.
  A simulated scene or replay of trajectory commands is not a live policy run.
  Mixed mode should be split into truthful continuous intervals/takes, not hidden.
- `policy.name`: model family/version; `checkpoint_id`: shareable name, revision or
  hash, never a token or private absolute path. Unknown is acceptable when disclosed.
- `inference.name`: active strategy, with any verified timing/chunk/sampling values
  in `inference.settings`. Do not infer settings from a filename or visual behavior.
- `session_id`: corresponding real run identifier if available; null otherwise.
- `config_label` / `config_sha256`: shareable config label and file SHA-256 if known.
  Do not attach the full config merely to fill provenance fields.
- `execution_evidence`: concise basis for evidence mode, e.g. the operator observed
  the policy-controlled arm through the live camera during this session. Clearly
  state when the source is an older recording rather than a newly captured run.
- `task_outcome`: `success`, `failure`, or `unknown`; `outcome_basis`: actual operator
  assessment or record that supports a claimed success/failure. None is inferred
  from GUI state alone. Success is not a condition for submitting honest footage.
- `camera_names`: public view labels; `gui_physical_camera_visible`: true only if
  a live camera of the physical robot/workspace is visible in the GUI recording.
- `capture_issues`: observed dropouts/freezes/latency or other defects, else [].
- `visual_reviewed`: true only after watching the full nominated interval.
- `gui.path`: e.g. `clips/take-001/gui.mp4`. `suggested_in_seconds` and
  `suggested_out_seconds`: relative to this submitted file, not the original if
  an intentional trim was made. Nominate ≥12 seconds, preferably 12–20.
- `external_robot`: null or an object with `path`, `offset_from_gui_seconds`
  (number or null), and `sync_method`. See shots.md for the offset sign convention.
- `evaluation_clip`: null or an object with `path`.
- `evaluation`: null or the actual operator's `score`, `scale`, `assessor_label`,
  `saved_record_id`, and `save_evidence`. Missing values remain null. Example scale
  could be 0–5, but use the local study's real schema; do not impose this example.

A station with multiple embodiments can make separate submissions, which avoids
ambiguous station-level embodiment labels. A station with different policies/tasks
on one embodiment can add takes to the same manifest.

## Folder sent back

```text
<station>-<date>.zip
  manifest.json
  validation.json
  SHA256SUMS
  clips/
    take-001/
      gui.mp4
      gui.source.json           # only when normalized using the helper
      external.mp4              # optional
      evaluation.mp4            # optional
    take-002/...
```

`validation.json` records technical properties, hashes, successful decode checks,
limitations and real-policy take IDs. Passing technical checks does not independently
verify the claimed robot/model/outcome. `pack` refuses invalid data and missing decode
checks. It includes only manifest-declared media and normalization sidecars, not
arbitrary files in the submission directory. Keep outputs outside the skill folder.

The contributor sends this ZIP to the coordinator. The coordinator may place all
station ZIPs in one outer archive without renaming their clip contents. Include the
station label in each ZIP filename to avoid collisions. Do not send the source skill
again as a footage submission, and do not combine clips into a collage locally.
